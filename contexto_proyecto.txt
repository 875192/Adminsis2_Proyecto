1. DESCRIPCIÓN GENERAL
--------------------------------------------------------------------------------

Sistema de monitorización distribuido con tolerancia a fallos para entornos Linux.
Gestiona N servidores y N clientes de forma autónoma sin intervención del
administrador. Se adapta automáticamente ante caídas de nodos.

Tecnologías:
  - Lenguaje: Python 3.8+
  - SO objetivo: Linux (Ubuntu/Debian)
  - Monitorización: Zabbix con stack LAMP (Apache, MySQL, PHP)
  - Comunicación: TCP puro (sin framework)
  - Puerto fijo: 9000 (configurable en config.json)
  - Control de versiones: Git (GitHub)

4. PROTOCOLO DE MENSAJES TCP
--------------------------------------------------------------------------------

Todos los mensajes viajan por TCP en texto plano (UTF-8).
Los mensajes JSON usan el campo "type" para distinguir el tipo.

Mensaje                                     Dirección              Descripción
---------------------------------------------------------------------------
HEARTBEAT                                   Cliente → Servidor     Comprobación de vida periódica
HEARTBEAT_ACK                               Servidor → Cliente     Confirmación de que el servidor sigue activo
RECONNECT_REQUEST client server_caido=<ip>  Cliente → Nuevo Srv    Solicitud de reconexión tras caída
RECONNECT_OK                                Nuevo Srv → Cliente    Reconexión aceptada
CLIENT_DOWN client_ip=<ip>                  Servidor → Admin       Notificación de caída de cliente
LOAD_REQUEST                                Servidor → Servidor    Consulta de carga entre servidores
LOAD_RESPONSE <score>                       Servidor → Servidor    Respuesta con puntuación de carga (float)
REGISTER (JSON)                             Cliente → Servidor     Alta del cliente en el servidor
MONITOR_REQUEST <interval>                  Servidor → Cliente     Intervalo de monitorización asignado
METRICS (JSON)                              Cliente → Servidor     Envío de métricas capturadas
METRICS_OK                                  Servidor → Cliente     Métricas recibidas correctamente
REASSIGN <ip> <puerto>                      Servidor → Cliente     Redirigir a otro servidor con menos carga

Formato mensaje REGISTER (JSON):
  { "type": "REGISTER", "client_id": "<id>", "client_ip": "<ip>",
    "known_servers": ["ip:puerto", ...], "timestamp": <float> }

Formato mensaje METRICS (JSON):
  { "type": "METRICS", "client_id": "<id>", "client_ip": "<ip>",
    "timestamp": <float>, "metrics": { ... } }

== 5.1  src/cliente/monitorizacion/cliente_monitor.py ==
Propósito: Loop principal del cliente. Autodescubrimiento de servidor, registro,
captura de métricas, envío, y gestión de heartbeat y reasignación.

Imports: argparse, concurrent.futures, json, os, platform, pwd, shutil,
         socket, sys, threading, time

Funciones:
  _cargar_config() -> dict
      Carga config.json. Ruta relativa desde la raíz del proyecto.

  _descubrir_servidor(puerto: int, timeout: float=0.3) -> str | None
      Escanea la subred /24 local en paralelo (50 hilos, ThreadPoolExecutor).
      Prueba primero localhost. Devuelve la primera IP que responde en el puerto.
      Tiempo total ~2 segundos para una subred completa.

  _leer_texto(ruta: str) -> str
      Lee un fichero de texto con manejo de errores. Devuelve "" si falla.

  _interfaces_validas() -> list[str]
      Lista interfaces de red no-loopback desde /sys/class/net/.

  _tx_bytes_total() -> int
      Suma los bytes transmitidos (tx_bytes) de todas las interfaces válidas
      leyendo /sys/class/net/<iface>/statistics/tx_bytes.

  _usuarios_sistema() -> list[str]
      Lista usuarios del sistema con UID >= 1000 usando pwd.getpwall().

  _leer_meminfo() -> dict[str, int]
      Parsea /proc/meminfo y devuelve un dict {campo: valor_kb}.

  _almacenamiento() -> dict[str, Any]
      Uso de disco mediante shutil.disk_usage("/") y lista de dispositivos
      desde /sys/block/.

  _tarjetas_red() -> list[dict[str, str]]
      Detalles de interfaces: nombre, MAC (/sys/class/net/<iface>/address),
      estado operacional (/sys/class/net/<iface>/operstate).

  _leer_cpu_snapshot() -> tuple[int, int]
      Lee la primera línea de /proc/stat y devuelve (idle, total).

  _calcular_cpu_pct(anterior: tuple, actual: tuple) -> float
      Calcula % de uso CPU entre dos snapshots:
      uso = 100 * (1 - delta_idle / delta_total)

  _carga_media() -> dict[str, float]
      Devuelve promedios de carga 1/5/15 minutos usando os.getloadavg().

  capturar_metricas(id_cliente, cpu_anterior, tx_anterior, instante_anterior)
      -> tuple[dict, tuple, int, float]
      Función principal de captura. Recopila: info del sistema (platform),
      usuarios, % CPU, % memoria, ancho de banda (Bps subida).
      Devuelve (metricas_dict, nuevo_cpu_snap, nuevo_tx, nuevo_instante).

  _enviar_mensaje(ip: str, puerto: int, payload: dict) -> str | None
      Crea socket TCP, envía JSON serializado, lee respuesta (buffer 4096).
      Timeout: 5 segundos. Devuelve la respuesta en texto o None si falla.

  _registrar_cliente(ip, puerto, id_cliente, servidores, intervalo_default=5.0)
      -> float | None
      Envía REGISTER. Espera MONITOR_REQUEST <intervalo>. Devuelve intervalo
      o None si falla.

  _parsear_destino(texto: str) -> tuple[str, int] | None
      Parsea "REASSIGN <ip> <puerto>" y devuelve (ip, puerto).

  _intentar_reconexion(servidor_caido, servidores, timeout) -> tuple[str,int] | None
      Itera por los servidores conocidos (excluyendo el caído) enviando
      RECONNECT_REQUEST. Devuelve el primer servidor que responda RECONNECT_OK.

  _hilo_heartbeat(servidor_ref, srv_lock, servidores, config, terminar) -> None
      Hilo daemon. Envía HEARTBEAT cada HEARTBEAT_INTERVAL segundos.
      Si no recibe HEARTBEAT_ACK, incrementa contador de fallos.
      Tras MAX_FALLOS fallos consecutivos llama a _intentar_reconexion().
      Buffer recv: 1024 bytes.

  ejecutar(ip_servidor, puerto, id_cliente, servidores, intervalo_default=5.0)
      -> None
      Función principal: registra el cliente, inicia hilo heartbeat, entra en
      loop de monitorización. Maneja respuestas REASSIGN (migra a nuevo servidor).

Constantes hardcodeadas en este fichero:
  50       -- workers del ThreadPoolExecutor para escaneo
  0.3      -- timeout de descubrimiento (segundos)
  5        -- timeout de envío de métricas (segundos)
  1024     -- buffer recv del heartbeat (bytes)
  4096     -- buffer recv de métricas (bytes)

== 5.4  src/servidor/alta_servidor/alta_server.py ==
Propósito: CU1. Script de instalación de Zabbix + MariaDB para un nuevo servidor.
Debe ejecutarse con sudo.

Imports: os, subprocess, sys

Funciones:
  run(cmd, quiet=False, capture=False, input_data=None)

      Lanza SystemExit si el proceso falla (returncode != 0).

  require_root()
      Comprueba os.geteuid() == 0. Sale si no es root.

  import_zabbix_schema()
      Descomprime el schema SQL con zcat y lo importa en MariaDB
      mediante pipe: zcat schema.sql.gz | mysql zabbix.

  main()
      Dos modos de operación determinados por argumento --master-ip:

      Modo MASTER (primer servidor, sin --master-ip):
        1. Descarga paquetes deb de Zabbix 7.0 LTS
        2. Instala mariadb-server, zabbix-server-mysql, zabbix-frontend-php,
           zabbix-apache-conf, zabbix-sql-scripts, zabbix-agent
        3. Crea usuario y base de datos "zabbix" en MySQL
        4. Importa schema SQL de Zabbix
        5. Configura /etc/zabbix/zabbix_server.conf: DBPassword
        6. Configura /etc/mysql/mariadb.conf.d/50-server.cnf: bind-address=0.0.0.0
        7. Reinicia zabbix-server, zabbix-agent, apache2
        8. Habilita servicios con systemctl enable

      Modo SECUNDARIO (con --master-ip=<IP>):
        1. Misma instalación de paquetes
        2. NO instala MariaDB local
        3. Configura DBHost al master IP en zabbix_server.conf
        4. Configura PHP para frontend
        5. Reinicia servicios

Credenciales hardcodeadas:
  Usuario DB:   zabbix
  Password DB:  Zabbix_Pass1
  Nombre nodo:  "Nodo Zabbix Secundario"

Nota de seguridad: Las credenciales de BD están en texto plano en el script.
No hay cifrado ni gestión de secretos.

== 5.7  src/servidor/monitorizacion/metricas.py ==
Propósito: Cálculo de la carga del servidor y almacenamiento de datos monitorizados.

Imports: json, os, platform, time

Funciones:
  _leer_meminfo() -> dict[str, int]
      Parsea /proc/meminfo. Devuelve {campo: valor_kb}.

  obtener_metricas_servidor() -> dict[str, Any]
      Recopila: hostname, núcleos CPU (os.cpu_count()), promedios de carga
      1/5/15 minutos, % memoria usada, timestamp.

  calcular_carga(tiempos_monitorizacion: list, clientes_activos: int)
      -> dict[str, Any]
      Calcula la puntuación de carga compuesta del servidor:

      Componentes:
        tiempo_ms   = media(tiempos_monitorizacion) * 1000
        load_norm   = min(100, (loadavg_1 / cores) * 100)
        mem_pct     = (usada / total) * 100 desde /proc/meminfo
        clientes    = clientes_activos

      Fórmula:
        score = min(100.0,
          tiempo_ms * 0.20 +    (peso 20%: latencia de monitorización)
          load_norm * 0.45 +    (peso 45%: carga CPU normalizada)
          mem_pct   * 0.25 +    (peso 25%: presión de memoria)
          clientes  * 3.5       (3.5 puntos por cliente, sin límite superior)
        )

      Devuelve dict con score, componentes individuales, timestamp.

  guardar_carga(ruta: str, carga: dict) -> None
      Escribe la carga actual como JSON en carga_srv<id>_<puerto>.json.
      Sobreescribe en cada llamada (fichero de estado, no histórico).

  registrar_datos_monitorizados(ruta: str, datos: dict) -> None
      Añade los datos de monitorización como línea JSON al fichero
      datos_monitorizados.log (append mode).

Propósito: Servidor TCP principal. Registra clientes, procesa métricas,

Imports: argparse, json, os, platform, socket, socketserver, sys, threading, time

         from tolerancia_fallos.monitor_clientes import iniciar_watchdog

Clases:

      Estado compartido entre todos los hilos del servidor.

      registrar_cliente(client_id, client_ip, known_servers) -> None

      actualizar_metricas(client_id, payload, tiempo) -> None
          Actualiza last_seen y métricas del cliente. Añade tiempo a la lista
          (máximo 50 entradas, elimina el más antiguo si se supera).

      obtener_carga() -> dict
          Llama a calcular_carga() con los tiempos y número de clientes actuales.

      candidato_reasignacion() -> tuple[str, int] | None
          Consulta a todos los servidores conocidos su carga (LOAD_REQUEST).
          Si alguno tiene score < (carga_local - umbral), lo devuelve como candidato.

  _ThreadingTCPServer(socketserver.ThreadingTCPServer)
      Subclase con allow_reuse_address = True para evitar "Address already in use".

  _Handler(socketserver.BaseRequestHandler)
      Manejador de conexiones. Un hilo por conexión (ThreadingTCPServer).

      handle() -> None
          Lee hasta 65535 bytes del socket.
          Detecta tipo de mensaje por prefijo de texto:

          "HEARTBEAT":
            → Responde "HEARTBEAT_ACK"
            → Actualiza last_seen del cliente

          "RECONNECT_REQUEST client server_caido=<ip>":
            → Responde "RECONNECT_OK"
            → Registra evento RECONEXION en el log
            → Actualiza last_seen del cliente

          "LOAD_REQUEST":
            → Calcula carga actual
            → Responde "LOAD_RESPONSE <score>"

          "REGISTER" (JSON con type="REGISTER"):
            → Llama a estado.registrar_cliente()
            → Registra evento ALTA_CLIENTE en el log
            → Responde "MONITOR_REQUEST <intervalo>"

          "METRICS" (JSON con type="METRICS"):
            → Llama a estado.actualizar_metricas()
            → Guarda métricas en log y fichero de carga
            → Consulta candidato de reasignación
            → Si existe candidato: responde "REASSIGN <ip> <puerto>"
                                   registra evento REASIGNACION en log
            → Si no: responde "METRICS_OK"

Funciones:
  _cargar_config() -> dict[str, Any]
      Carga config.json.

  _ruta_log_eventos(config: dict) -> str
      Devuelve la ruta absoluta del log de eventos desde LOG_PATH en config.

  _ruta_log_datos() -> str
      Ruta al fichero datos_monitorizados.log.

  _ruta_carga(id_servidor: str, puerto: int) -> str

  _consultar_carga(ip: str, puerto: int) -> float | None

  _parsear_servidores(textos: list[str]) -> list[tuple[str, int]]

  ejecutar(host, puerto, id_servidor, servidores, umbral_reasignacion) -> None

        2. Crea EstadoMonitor
        3. Inicia watchdog (iniciar_watchdog)

--------------------------------------------------------------------------------
6. ALGORITMOS CLAVE
--------------------------------------------------------------------------------

-- Autodescubrimiento de servidor (cliente_monitor.py: _descubrir_servidor) --
  1. Prueba localhost:PUERTO (0.3s timeout)
  2. Si falla: obtiene la subred /24 local desde socket.gethostname()
  3. Lanza 50 hilos en paralelo (ThreadPoolExecutor)
  4. Cada hilo prueba una IP de la subred con timeout 0.3s
  5. Devuelve la primera IP que responde
  6. Tiempo total aproximado: ~2 segundos para /24 completo

-- Cálculo de uso de CPU (cliente_monitor.py: _leer_cpu_snapshot / _calcular_cpu_pct) --
  Snapshot = (idle, total) leído de la primera línea de /proc/stat
  idle  = campo 4 (idle time)
  total = suma de todos los campos
  uso % = 100 * (1 - delta_idle / delta_total)

-- Cálculo de ancho de banda de subida (cliente_monitor.py) --
  tx_bytes_total() suma /sys/class/net/<iface>/statistics/tx_bytes de todas las
  interfaces válidas. La tasa se calcula como:
    ancho_banda_bps = (tx_actual - tx_anterior) / (tiempo_actual - tiempo_anterior)

-- Puntuación de carga del servidor (metricas.py: calcular_carga) --
  score = min(100.0,
    media(tiempos_ms) * 0.20 +    20% latencia monitorización
    load_norm         * 0.45 +    45% carga CPU (loadavg_1 / cores * 100)
    mem_pct           * 0.25 +    25% memoria usada
    clientes_activos  * 3.5       3.5 puntos por cliente (sin límite)
  )
  Ejemplo (3 clientes, 2ms, loadavg=0.5 en 4 cores, mem=30%):
    = 0.4 + 5.625 + 7.5 + 10.5 = 24.025

-- Detección de caída y reconexión (hilo heartbeat / detector_servidor.py) --
  1. Envía HEARTBEAT cada HEARTBEAT_INTERVAL (3s)
  2. Espera HEARTBEAT_ACK con timeout HEARTBEAT_TIMEOUT (5s)
  3. En fallo: incrementa contador
  4. Tras MAX_FALLOS (3) fallos consecutivos → tiempo mínimo de detección: 9s
  5. Llama a intentar_reconexion() con la lista de servidores conocidos
  6. Si encuentra nuevo servidor: actualiza referencia y resetea contador
  7. Si no encuentra ninguno: termina el proceso (RU-3)

-- Balanceo de carga (servidor_monitor.py: candidato_reasignacion) --
  1. Calcula la carga propia
  2. Para cada servidor conocido: envía LOAD_REQUEST (timeout 2s)
  3. Si score_remoto < score_local - umbral_reasignacion:
       → El servidor remoto es candidato
  4. Envía REASSIGN al cliente con la IP del candidato
  5. El cliente se desconecta y registra con el nuevo servidor

--------------------------------------------------------------------------------
7. FLUJO DE DATOS DEL SISTEMA
--------------------------------------------------------------------------------

ARRANQUE SERVIDOR:
  1. alta_server.py → instala Zabbix + MariaDB (solo una vez)
  2. servidor_monitor.py → crea EstadoMonitor, inicia watchdog, escucha TCP

ARRANQUE CLIENTE:
  1. alta_cliente.py → instala agente Zabbix (solo una vez)
  2. cliente_monitor.py → descubre servidor, se registra, entra en loop

LOOP NORMAL (sin fallos):
  Cliente:
    Cada MONITOR_INTERVAL segundos:
      capturar_metricas() → _enviar_mensaje(METRICS) → recibe METRICS_OK
    Cada HEARTBEAT_INTERVAL segundos (hilo paralelo):
      Envía HEARTBEAT → recibe HEARTBEAT_ACK

  Servidor (por conexión entrante, hilo separado):
    REGISTER → registra cliente, responde MONITOR_REQUEST
    METRICS → actualiza estado, calcula carga, consulta otros srvs, responde
    HEARTBEAT → responde ACK, actualiza last_seen

  Servidor (watchdog, hilo continuo):
    Cada HEARTBEAT_INTERVAL segundos: revisa last_seen de todos los clientes

CAÍDA DE CLIENTE (detectada por servidor):
  _watchdog detecta last_seen > umbral (9s)
  → _log(CAIDA_CLIENTE, client_ip=...)
  → notificar_admin(client_ip) → envía CLIENT_DOWN al admin por TCP
  → Elimina cliente del estado

CAÍDA DE SERVIDOR (detectada por cliente):
  _hilo_heartbeat acumula MAX_FALLOS fallos
  → _intentar_reconexion(servidor_caido, servidores_conocidos)
  → Envía RECONNECT_REQUEST al nuevo servidor
  → Nuevo servidor responde RECONNECT_OK, registra evento RECONEXION
  → Cliente actualiza referencia al servidor y continúa

REASIGNACIÓN POR CARGA:
  Servidor recibe METRICS, calcula su carga, consulta otros servidores
  → Si existe servidor con menos carga (diferencia > umbral)
  → Responde REASSIGN <ip> <puerto> al cliente
  → Servidor registra evento REASIGNACION
  → Cliente llama a _parsear_destino(), migra al nuevo servidor

11. NOTAS DE DISEÑO Y DECISIONES TÉCNICAS
--------------------------------------------------------------------------------

- No hay dependencias externas de Python. Todo es stdlib.
- Concurrencia con threading (no asyncio). GIL limita paralelismo real de CPU.
  Aceptable porque el cuello de botella es I/O de red, no CPU.
- socketserver.ThreadingTCPServer: un hilo por conexión entrante.
- El estado compartido (EstadoMonitor) usa un Lock para operaciones de escritura.
- Los tiempos de monitorización se almacenan en una lista con tope de 50 entradas
  para evitar crecimiento ilimitado de memoria.
- La comunicación inter-servidor para consulta de carga (LOAD_REQUEST) tiene
  timeout corto (2s) para no bloquear el handler del cliente esperando.
- El cliente mantiene una lista de todos los servidores conocidos (se actualiza
  con los que otros clientes reportan al registrarse).
- No hay autenticación ni cifrado en ningún punto del protocolo TCP.
- Los ficheros de setup (alta_server.py, alta_cliente.py) son scripts de
  ejecución única, no módulos importables. Usan subprocess directamente.
- Zabbix se usa como motor de monitorización de infraestructura; los scripts
  Python son la capa de automatización, registro de eventos y tolerancia a fallos.

--------------------------------------------------------------------------------
12. POSIBLES MEJORAS / PUNTOS PENDIENTES
--------------------------------------------------------------------------------

- No hay receptor implementado para la notificación CLIENT_DOWN del admin.
- La contraseña de la BD de Zabbix está hardcodeada en alta_server.py.
- No hay integración directa entre alta_cliente.py y cliente_monitor.py
  (son dos pasos manuales separados).
- El autodescubrimiento de subred en cliente_monitor.py usa socket.gethostname()
  para obtener la IP local, lo que puede fallar en configuraciones no estándar.
- No se verifica que el servidor encontrado sea el correcto (sin autenticación).
- El balanceo de carga usa umbral fijo; no hay historial de cargas para decisiones
  más inteligentes.
- Los tiempos de monitorización (hasta 50) y la fórmula de carga son aproximaciones
  que deberían calibrarse con métricas reales del sistema.
